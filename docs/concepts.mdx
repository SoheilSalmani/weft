# Concepts

## The rendering equation

```
render(base, answers, patches) → tree
```

Rendering is a pure function. A template is not a directory of files with
holes in it; it is a **patch DAG** replayed over an empty tree. The initial
scaffold is itself just the first patch (a set of `create_file` ops).

Determinism is load-bearing: patches apply in topological order of the
dependency DAG with ties broken by patch id, so the order patches happen to be
listed or loaded in never matters. Two renders of the same inputs are
byte-identical — that's what makes `update`'s 3-way merge sound.

## Patches

A patch is one recorded unit of template behavior:

| Field        | Meaning                                                        |
| ------------ | -------------------------------------------------------------- |
| `id`         | blake3 hash of the canonical serialization (computed, never stored) |
| `depends_on` | explicit dependencies — ids of other patches                   |
| `when`       | optional Starlark gate; false skips the patch *and its dependents* |
| `ops`        | the operation list                                             |

Because the hash covers dependency *ids*, patch ids form a Merkle DAG:
changing any patch changes the id of everything downstream. A scaffolded
project pins the exact ids it was rendered from.

**Independent patches must commute.** If two patches have no dependency path
between them, applying them in either order must produce the same tree.
`weft check` verifies this pairwise. If two patches don't commute, one must
depend on the other.

## Operations and segments

Ops are tree edits: `create_file`, `modify_file`, `delete_file`,
`rename_path`, `set_mode`. Paths and file content are sequences of
**segments**:

```json
["# ", {"answer": "project_name"}]
```

- a plain string is a **literal**
- `{"answer": "id"}` substitutes an answer value at render time
- `{"expr": "..."}` evaluates a Starlark expression at render time

Content is line-granular: a file is a list of lines, each line a list of
segments (fully-literal lines collapse to plain strings, so patch files stay
readable and hand-writable).

## Context-anchored hunks

`modify_file` carries hunks that are **anchored by context, never line
numbers**:

```json
{
  "context_before": ["Scaffolded by weft."],
  "removed": [],
  "added": ["", "Ships with Docker."],
  "context_after": []
}
```

At render time the pattern `context_before + removed + context_after` must
match **exactly once** in the target file: zero matches and multiple matches
are distinct, clean errors ("the file diverged" vs "the context is
ambiguous"). This is what lets patches survive reordering and composition —
a hunk lands wherever its context is, not at line 42.

Context lines participate in value abstraction too: if the base render put
`# My Demo` in a file, the recorded context is `["# ", {"answer":
"project_name"}]`, so the hunk still matches when someone scaffolds with a
different name.

## Value abstraction at commit

Recording is concrete; abstraction is deferred to `weft commit`:

1. The worktree is diffed against a re-render of the pinned base.
2. Every string/choice answer value (length ≥ 2) found verbatim in the
   changed content, context lines, or paths is proposed as a substitution —
   longest value wins on overlap.
3. You confirm per answer (or `--yes` accepts all exact matches).
4. **Secret values are abstracted unconditionally** — a literal secret in a
   patch file would be persistence, which weft never allows.
5. The candidate patch is replayed against the base; if it doesn't reproduce
   the worktree byte-for-byte (e.g. an ambiguous context), commit refuses to
   write it.

## Answers, layering, precedence

Questions live in `weft.toml`. Concrete values arrive in layers, later wins:

```
Starlark defaults → presets (CLI order) → answers file → --answer flags → prompts
```

Conflicts at *equal* precedence (the same `--answer` twice with different
values) are errors, not silent overrides. Presets are nothing special — just
partial answer-sets in TOML files.

## Tasks

Tasks are nodes in the same dependency graph as file changes:

```toml
[[task]]
id = "uv-sync"
inputs = ["glob:pyproject.toml", "glob:uv.lock"]
action = "uv sync"
```

Inputs name file globs, answers, or other tasks. On first scaffold every
`when`-passing task fires; on `update`, a task fires only if a `glob:` input
matches a file that changed between the old and new renders, an `answer:`
input's value changed, or an upstream `task:` input fired.

## The two state files

| File                              | Owner            | Contents                                    |
| --------------------------------- | ---------------- | ------------------------------------------- |
| `<project>/.weft/state.toml`      | scaffolded app   | template path, pinned patch ids, answers (secrets as refs) |
| `<template>/.weft-record/`        | recording session| pinned base ids, base tree hash, answers, the scratch worktree |

Neither ever contains a resolved secret value; the core type system enforces
it (serializing `Value::Secret` is an error by construction).
