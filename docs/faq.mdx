# FAQ

### How is this different from Copier / Cookiecutter?

Those tools store **templates of outputs**: files with Jinja placeholders
that expand at scaffold time. Weft stores **patches of inputs**: you edit
real rendered files, and the tool captures (operations + answer references).
Consequences:

- template files are valid files — editors, linters, and formatters work on
  them directly during recording;
- updates are a true 3-way merge against a reproducible base, not a
  re-render + overlay;
- features compose as patches with explicit dependencies instead of
  `{% if %}` blocks threaded through every file.

### Why must independent patches commute?

Because rendering applies patches in dependency order with ties broken by
content id — if two unordered patches interfered, the output would depend on
an arbitrary tiebreak. `weft check` applies every independent pair in both
orders and compares tree hashes; if they differ (or one order fails), you're
told to add a dependency. This is the Pijul-flavored part of the design.

### What happens if a hunk doesn't apply?

Rendering fails with a clean, specific error: either "context not found" (the
file diverged from what the patch was recorded against) or "context is
ambiguous" (it matches in N places). Nothing is partially applied to disk —
rendering happens in memory and only a successful tree is written.

### Why did commit refuse my patch with "does not reproduce the worktree"?

Before writing, `weft commit` replays the candidate patch against the base
render and requires byte-identical output. The usual cause is an ambiguous
hunk: your edit's surrounding context appears more than once in the file.
Make the edit's neighborhood more distinctive (or split the change) and
re-commit.

### Can I edit a committed patch file by hand?

Yes — the JSON format is designed for it (deps by name, plain strings for
literal lines). Ids are recomputed from content on every load, so there's
nothing to keep in sync manually. Run `weft check` afterwards; note that
editing a patch changes its id and therefore the id of every patch downstream
of it, which breaks `weft update` for projects pinned to the old ids. Treat
published patches as immutable; append new ones instead.

### Where do secrets go?

Nowhere — that's the point. Files store only references like
`env:DATABASE_URL`; values resolve at render time, can't be serialized (the
core type errors), can't enter Starlark, and are force-abstracted out of
recorded patches. See [Secrets](./guides/secrets).

### Does `weft update` re-run all tasks?

No. Tasks declare inputs (`glob:`, `answer:`, `task:`) and re-fire only when
an input changed **between the old and new template renders**. Your local
edits never trigger tasks, and on a conflicted update tasks are skipped
entirely and reported.

### Why is my file's trailing whitespace different after scaffolding?

The MVP normalizes every rendered text file to end with exactly one trailing
newline (empty files stay empty). This keeps hashing, diffing, and merging
line-granular and predictable. Binary and byte-exact files are on the
[roadmap](./roadmap).

### Is the template a git repo? Does weft use git?

Weft doesn't use git at all — no `git2`, no shelling out. Templates and
projects are plain directories; you're free to version them with git (weft
skips `.git/` when reading trees). Pinning is done with weft's own
content-addressed patch ids, not git commits.

### What platforms are supported?

Linux and macOS are tested. Windows isn't gratuitously broken but carries no
guarantees in the MVP (file modes are a no-op there).
