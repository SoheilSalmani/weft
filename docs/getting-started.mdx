# Getting started

## Requirements

- Rust toolchain (weft is developed against Rust 1.90+)
- Linux or macOS (Windows is untested in the MVP)

## Build

```sh
git clone <your-weft-checkout>
cd weft
cargo build --release
# single static-ish binary:
./target/release/weft --version
```

For development, the full gate is:

```sh
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace     # run workspace-wide so e2e tests find the binary
```

## Scaffold a project

Templates are local directories containing a `weft.toml`. The repo ships a
small fixture template you can try immediately:

```sh
weft new fixtures/templates/hello /tmp/demo --answer "project_name=My Demo"
```

What happened:

- Questions were answered from three places, in precedence order: your
  `--answer` flag, Starlark defaults (`package_name` derived
  `my-demo` from the project name), and interactive prompts for anything
  left (none here).
- The patch DAG rendered deterministically into `/tmp/demo`.
- `.weft/state.toml` was written: it pins the template path, the exact patch
  ids the tree was rendered from, and your answers — this is what makes
  `weft update` possible later.
- The template's tasks ran (here: a marker file proving the task graph
  fired).

## Non-interactive use

Weft auto-detects a missing TTY and switches to non-interactive mode, or you
can force it:

```sh
weft new tpl out --answer project_name=ci-run --non-interactive
```

Unanswered questions without defaults fail with the exact `--answer` flag to
pass — designed for CI.
