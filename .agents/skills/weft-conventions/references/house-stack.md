## Every repository: the `base` template

Three rules follow from it:

- The trackers are **bools, not a choice**: choice values are abstracted wherever they appear and `linear` is all over the skill prose (`questions.md`).
- Every stack template extends `base` and keeps no copy of it: change shared scaffolding in `base` alone. `weft patch amend` in a stack refuses an inherited patch, and a copied patch file stops the stack loading, because names are one namespace across `extends`. For the same reason a stack's own root is named after the stack (`dbt`), not `base`; it depends on base's root, adds the stack's ignores as a hunk at the top of base's `.gitignore`, and either keeps base's README or deletes it and writes its own. A stack setup hook whose output belongs in the first commit declares `before: ["git-commit"]`, since base cannot name its extenders' hooks, and a stack rewords or narrows base's questions with `[refine.<id>]`. In the templates repository, `scripts/sync-skills.sh` re-records base's skills patches from the skills repository, and CI runs `scripts/check-templates.sh` (`weft check` on every template, then a render proving the `commit_*` answers).
- The `commit_*` questions keep tooling out of git with the committed `.gitignore`, never `.git/info/exclude`: every clone ignores it, and nothing depends on a hook having run. A client's repository then carries only the ignore stanza; weft still renders and updates the files, which `.weftignore` must never list. Answering false on an existing repository does not untrack files already committed; `git rm -r --cached` them.

## Pinned, not asked

- Language and tool versions: `node`, `java`, `uv`, `astro`, `pnpm` in `mise.toml`; `.python-version`; `packageManager`; the Gradle wrapper version; `scalafmt`; Spring Boot; the shadcn CLI as a devDependency, which the generated component patches run. Bump with `weft patch amend`; `weft update` moves every project. `java_version` was dropped from `java` on 2026-09-25. `scala` still asks `scala_version`, a 2.13-versus-3 axis rather than a plain version; do not add version questions elsewhere.
- Lockfiles: never in a patch. `uv.lock`, `pnpm-lock.yaml`, `gradle.lockfile` are produced by a `setup` hook with `inputs` on the manifest. List them in `.weftignore`.
- Formatter and linter configuration: shipped, not offered.
- Editor and git configuration, AGENTS.md, the skills, the MCP file set, the Paseo worktree setup and worktree seeding: shipped by `base`, never asked. The `commit_*` questions ask only whether each is committed or gitignored, because a client's repository must not carry personal agent tooling.

## Not yet decided

No template ships a LICENSE, pre-commit, ruff or mypy configuration, a justfile or Makefile, a devcontainer, or Renovate outside `java`. When a new template needs one of these, decide once, write it into the patch, and add the decision here. Do not turn the absence of a decision into a question.

## Defects in the existing templates

Steer away from these; they are not conventions:

- `java` is a chain `java → testing → formatter → linter → spring-boot` because every patch edits the same `plugins {}` and `dependencies {}` blocks of `build.gradle.kts` and each hunk anchors on the previous patch's lines. That is the legitimate shared-config case, not a smell. `weft share` does not reach it: it shares only a file the patches each create, and here `java` creates the build file and the others change it, which `share` refuses. Do not flatten it by re-parenting, because the hunks do anchor on each other. The Gradle build, its wrapper and the entry point are one `java` patch: a Gradle project without its wrapper is not a state anyone wants.
- `weft hook ls` lists hooks in declaration order, so `git-commit` shows before the setup hooks it runs after; `weft describe --json` and the actual run honour the order. Display only.
- `web-template` and `python-service` do not match their directory names.
