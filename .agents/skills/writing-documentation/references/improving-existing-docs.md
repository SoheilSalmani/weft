# Improving documentation that already exists

Most documentation work is not writing a new page. It is repairing pages that grew without a plan.

## Do not plan a restructure

The instinct on meeting Diátaxis is to audit everything and design a new structure. Resist it.

A large reorganisation delays every benefit until it is complete, and it usually is not completed. It also requires deciding the shape of documentation you have not written yet, which is the decision you are least equipped to make.

Instead, ask one question: **what is the single thing I could improve right now?** Do that, then ask again. The structure emerges from repeated small corrections, and each one delivers value on the day it is made.

This is not a compromise. It is how the framework is meant to be used. Understanding it fully is not a prerequisite for applying it usefully.

## Diagnosing a document

Read the document and ask the compass questions of each section rather than of the whole.

A document whose sections give different answers is mixed. This is the most common fault and the most damaging, because the reader cannot tell which parts to trust for which purpose.

Signs, in order of how often they appear:

**A tutorial that explains.** Paragraphs of background between steps. The learner is trying to concentrate and is being asked to reflect.

**A how-to guide that teaches.** It defines terms and explains what things are. The reader already knew, and has now been slowed down.

**Reference that advises.** `Should`, `recommended`, and `we suggest` appear. Reference states what is; advice is a different mode.

**Explanation that instructs.** Imperative sentences appear in a discussion. The reader was thinking, not working.

**A page that is four documents.** Often called `Overview` or the product's own name. It usually accumulated rather than being written.

## Splitting a mixed document

1. **Mark each section with its mode.** Use the compass. Sections that resist classification are usually two sections.
2. **Cut along the mode boundaries.** Do not rewrite yet. Move the material as it stands.
3. **Give each piece a title in its mode's form.** `How to x`, `About x`, the name of the thing, or the lesson.
4. **Link them to each other.** Every split creates a place a reader might have expected the other half.
5. **Only now, rewrite.** Each piece can be repaired properly once it has one job.

Do the cut before the rewrite. Rewriting a mixed document usually produces a better mixed document.

## Deciding what to fix first

Prefer, in this order:

1. **Anything that is wrong.** A false statement outranks every structural concern, because it actively misleads.
2. **The document readers hit first.** Usually the entry point or getting started page. Failures there lose readers permanently.
3. **The missing mode.** Most projects have reference and some how-to guides, and no tutorial and no explanation. The gap is usually explanation, because it is the hardest to write and the easiest to postpone.
4. **The mixed documents**, largest first.
5. **Style and consistency.** Real, but last. A well-written document in the wrong mode is still in the wrong mode.

## Knowing when to stop

Documentation is never finished, and treating it as a project with an end produces a burst of work followed by years of drift.

Better to make it routine: when the product changes, the documentation changes with it, in the same review. Documentation that lives beside the code and is reviewed with it stays close to true. Documentation kept elsewhere drifts, whatever anyone intends.
